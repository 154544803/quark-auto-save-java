# quark-auto-save Java Web 控制台 UI 渐进优化设计

## 背景

当前 Web 控制台已经具备登录、账号管理、任务管理、手动执行、历史查看和配置保存能力，前端采用 Thymeleaf 模板 + 单文件 CSS + 原生 JavaScript 的轻量实现。这种结构便于快速落地，但在当前版本中仍存在以下问题：

- `dashboard` 各区块视觉权重接近，主次关系不清晰
- `login` 页面过于朴素，与控制台主页面缺少统一的品牌感
- 卡片、面板、抽屉的层级语言接近，导致页面“整齐但不突出”
- 表单抽屉分组较弱，说明文案、输入区域和操作区之间的呼吸感不足
- 部分模板和脚本文案存在中文乱码，直接影响 UI 可读性

本次工作目标不是推倒重做前端，而是在保持现有业务逻辑、接口调用、事件绑定和数据流不变的前提下，对 `login + dashboard` 做一次可落地、低风险的界面升级。

## 目标

- 保持现有功能、交互和数据流不变，重点优化视觉表现与信息层级
- 保留浅暖底色、低饱和绿色和轻玻璃感，统一 `login` 与 `dashboard` 的视觉语言
- 将 `dashboard` 从“多个并列模块”收敛为“顶部概览 + 主工作区 + 辅助信息区”
- 优化卡片、抽屉、表单、按钮和提示信息的层级与留白
- 修复前端模板与脚本文案中的乱码问题，确保 UTF-8 可读性
- 保持代码结构简单可维护，不引入新的重型依赖

## 非目标

- 不修改接口参数、后端控制器、请求流程或业务校验逻辑
- 不引入新的前端框架、构建工具或 UI 组件库
- 不重写整套页面交互，仅在现有结构上做渐进式优化
- 不调整权限控制、路由跳转、抽屉打开关闭机制和保存逻辑

## 现状诊断

### 1. 页面结构问题

当前 `dashboard` 页面虽然已经按 `hero / accounts / tasks / history / config` 分区，但各模块基本是并列展示，缺少明显的浏览顺序。用户进入页面后，无法快速区分：

- 什么是当前系统状态
- 什么是核心工作区
- 什么是低频辅助功能

### 2. 信息层级问题

当前 `hero-card`、`panel`、`config-card`、`history-item` 的视觉语言接近，导致以下问题：

- 顶部概览区没有成为真正的视觉入口
- 账号区和任务区的重要性没有拉开差距
- 历史记录和配置操作与主工作区抢注意力

### 3. 表单体验问题

抽屉表单已具备清晰的字段分组，但仍有以下不足：

- 分组标题与表单字段之间的节奏不够明显
- 说明文案存在但可读性偏弱
- 删除、取消、保存等动作的主次关系不够稳定
- 聚焦态、悬停态和禁用态反馈偏弱

### 4. 登录页一致性问题

`login` 页面与控制台主体共用样式文件，但当前只停留在基础表单展示层面，未能建立统一的品牌气质和产品入口感。

### 5. 文案可读性问题

当前模板与前端脚本内存在中文乱码，必须在本次 UI 优化中同步修复，否则界面升级后仍无法满足可用性要求。

## 方案对比

### 方案 A：低风险增强型

保留当前双列骨架，主要优化 hero、卡片、按钮、抽屉和登录页的样式表现。

优点：

- 改动最小
- 对现有模板和脚本兼容性最高

缺点：

- 层级改善有限
- 难以明显体现“展示型后台”的结构提升

### 方案 B：展示型后台

保留现有 section 与核心 ID，不调整业务流；通过重新组织 `dashboard` 布局，形成“顶部概览 + 左侧主工作区 + 右侧辅助信息区”的结构。

优点：

- 最符合“浅暖底色 + 低饱和绿色 + 轻玻璃感 + 偏舒展展示型后台”的目标
- 可以显著改善信息层级
- 仍可复用现有模板结构、样式体系和事件绑定

缺点：

- 相比方案 A，需要适度调整模板结构和较多 CSS

### 方案 C：单列舒展型

将所有核心区块纵向排布，以更大的留白和更长的滚动距离换取视觉舒展度。

优点：

- 视觉最轻松
- 易于形成统一的大卡片风格

缺点：

- 桌面端空间利用率偏低
- 当账号和任务数量增长后，浏览成本上升

## 最终选择

选择方案 B：展示型后台。

原因：

- 与当前项目的模板结构兼容性最高
- 能在不动业务逻辑的情况下明显提升页面层级
- 兼顾“展示感”和“后台效率”，比方案 C 更适合持续管理场景

## 页面结构设计

## Dashboard

### 顶部概览区

保留现有 `hero-card` 全宽区域，但重组为左右两段：

- 左侧：页面标题、简短说明、4 个统计卡片
- 右侧：主操作按钮区

统计项继续复用当前逻辑：

- 账号数量
- 任务数量
- 已启用任务数
- 最近执行时间

按钮区保留现有行为：

- `run-all`
- `logout-button`

视觉目标：

- 让 `hero-card` 成为页面第一个关注点
- 强化“状态概览”和“关键操作”的区分
- 收紧标题区高度，避免头部占用过多垂直空间

### 主工作区与辅助区

在 `hero-card` 下新增一个布局容器，用于组织页面主次关系：

- 左侧主栏：账号管理、任务管理
- 右侧辅栏：最近执行记录、配置操作

设计原则：

- 账号与任务是高频操作，放在主栏
- 历史记录与配置区是辅助功能，放在辅栏
- 在移动端下辅栏自然下移，不破坏阅读顺序

### 账号管理区

保留 `account-section` 和 `account-list`，以卡片列表方式展示：

- 账号名称
- Cookie 配置状态
- 关联任务数量
- 编辑按钮

优化方向：

- 账号卡片更克制，避免与任务卡片同等抢眼
- Cookie 继续掩码显示，不暴露完整内容
- 新增按钮仍保留在区块头部，不调整 ID 与绑定逻辑

### 任务管理区

保留 `task-section` 和 `task-list`，继续展示任务卡片列表。

任务卡片重点展示：

- 任务名称
- 启用状态
- 所属账号
- 保存路径
- 运行星期
- 结束日期
- 执行按钮
- 编辑按钮

优化方向：

- 任务区成为左侧主栏的视觉核心
- 状态信息和操作按钮分区更明确
- 卡片留白更充足，便于快速扫读

### 最近执行记录区

保留 `history-section` 和 `history-list`，放入右侧辅栏，作为“状态回顾区”。

优化方向：

- 弱化其与任务主区的竞争关系
- 保持摘要化展示，不扩展为复杂明细面板
- 空状态和成功/失败/跳过摘要继续保留

### 配置操作区

保留 `config-actions-section`、`config-message`、`advanced-config-panel` 等现有结构和行为，但调整其在页面中的位置和表现方式。

优化方向：

- 默认表现为工具卡，而不是内容主区
- 强调三个核心动作：
  - `validate-config`
  - `advanced-config-toggle`
  - `save-all-config`
- 高级 YAML 展开后，作为受控的高级编辑入口呈现

## Login

`login` 页面继续使用现有表单结构和提交流程，但强化其作为控制台入口页的品牌感。

设计方向：

- 延续与 `dashboard` 一致的浅暖背景和低饱和绿色
- 登录卡片更聚焦，形成明确的标题、副标题、表单和错误提示层级
- 保留当前 `login-form`、`username`、`password`、`login-error` 的 ID 和提交逻辑

## 视觉系统设计

### 色彩

- 继续采用浅暖色背景与低饱和绿色主色
- 降低绿色饱和度，减少按钮过于跳出的感觉
- 使用更温和的中性色做正文、辅助说明和边框

### 质感

- 保留轻玻璃感和柔和渐变背景
- 收敛阴影强度，避免所有组件都像同一层级
- 通过背景透明度、边框强弱和阴影深浅建立层次

### 字体层级

统一以下层级：

- `h1`：页面主标题
- `h2`：区块标题
- `h3`：卡片或表单组标题
- `subtitle` / `panel-description` / `field small`：辅助说明
- `eyebrow`：低调标签化信息，不再过度强调

### 按钮体系

保留现有按钮类名，但重新定义视觉主次：

- `primary-button`：登录、保存、执行等关键动作
- `secondary-button`：新增、编辑、模式切换
- `ghost-button`：低优先级或危险操作
- `icon-button`：抽屉关闭等辅助动作

## 表单与抽屉设计

保留现有抽屉交互、模板 ID 和事件逻辑，重点优化视觉节奏和可读性。

### 账号抽屉

保留字段：

- 账号名称
- Quark Cookie

优化方向：

- 标题区更清晰
- 说明文案更易读
- 删除按钮视觉弱化，但保持存在
- 底部动作区对齐更稳定

### 任务抽屉

继续保留三个逻辑分组：

- 基础信息
- 转存规则
- 调度限制

优化方向：

- 组标题、说明、字段之间建立更清晰的留白层次
- 输入框、下拉框、日期控件和星期选择组样式统一
- 聚焦态更明确，便于长表单填写

## 文案与编码要求

本次 UI 优化必须同步修复前端模板与脚本中的中文乱码，要求如下：

- 所有页面文案统一为可读中文
- 所有新增与修改文件按 UTF-8 保存
- 不引入新的乱码风险

## 实现边界

预计只修改以下前端文件：

- `src/main/resources/templates/dashboard.html`
- `src/main/resources/templates/login.html`
- `src/main/resources/static/css/web-console.css`
- `src/main/resources/static/js/web-console.js`

限制要求：

- 不修改接口路径、请求参数、响应结构
- 不修改后端控制器、服务、模型或持久化逻辑
- 不调整现有表单提交流程、抽屉开关逻辑和保存逻辑
- 不引入新的前端依赖

## 风险点

### 1. DOM 重排风险

如果调整 `dashboard` 模板结构，必须保证脚本依赖的元素 ID 不变，否则会影响现有绑定逻辑。

### 2. 中文文案修复风险

修复乱码时需要同时处理模板和脚本，避免一处修复、一处仍乱码导致体验不一致。

### 3. 响应式风险

右侧辅栏在窄屏下必须能自然下移，不能造成主工作区被压缩或遮挡。

## 测试与验证

### 自动化验证

至少执行与页面渲染和控制台入口相关的测试：

- `WebConsolePageRenderingTest`
- `WebConsolePageControllerTest`
- `WebConsoleAuthControllerTest`

如模板结构调整影响页面渲染断言，应同步更新测试，前提是行为未改变。

### 手工验证

- 登录页可正常输入与提交
- 登录成功后控制台页面正常渲染
- 账号卡片、任务卡片、历史区、配置区均正常显示
- 抽屉可以正常打开、关闭、提交与删除
- 高级 YAML 面板仍可展开与保存
- 移动端或窄屏下布局不会错位或遮挡

## 后续计划入口

在该设计确认后，下一步进入实现计划阶段，按以下顺序推进：

1. 先补充或调整页面渲染测试，确保 UI 改动有回归保护
2. 再调整模板结构与文案
3. 随后重构样式体系
4. 最后做前端脚本文案修复与必要的结构适配

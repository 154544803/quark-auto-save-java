# quark-auto-save Java Web 表单编辑与界面重构设计

## 背景

当前 Java Web 管理台已经具备登录、任务查看、手动执行和 `tasks.yml` 保存能力，但配置编辑区仍然直接暴露原始 YAML 文本框。这个方案适合作为第一版能力兜底，不适合作为常规用户入口，主要问题有：

- 普通用户需要直接编辑原始配置文本，理解成本高，容易误改格式
- 字段用途缺少明确说明，无法快速知道每一项应该填什么
- 主控制台视觉层次较弱，当前更像调试后台而不是正式管理台
- 配置区占据大量空间，但默认状态下并没有给出“账号”和“任务”的结构化编辑路径

本次设计目标是在不影响 `once` 模式和现有 GitHub Actions 执行链路的前提下，把配置编辑升级为“表单优先，高级模式保留 YAML”的体验，并同步提升整体 UI 质感。

## 目标

- 将常用配置字段从原始 YAML 编辑切换为结构化表单编辑
- 明确展示每个字段的用途、示例和校验提示
- 为账号和任务分别提供新增、编辑、删除的专用交互
- 保留原始 YAML 作为高级模式，而不是主入口
- 提升主控制台的视觉层次、信息密度和产品感
- 继续复用现有 `tasks.yml` 文件作为最终配置来源
- 保证 `once` 模式和 GitHub Actions 使用方式完全不变

## 非目标

- 第一版不追求覆盖 `tasks.yml` 的全部可能字段
- 不引入独立前端工程、Node 构建链或 SPA 框架
- 不引入数据库持久化配置
- 不改变现有任务执行服务和 `once` 模式语义
- 不在本次重构中加入复杂权限、多用户协作或审计日志

## 范围

第一版表单覆盖以下常用字段。

### 账号字段

- `name`
- `cookie`

### 任务字段

- `name`
- `account`
- `share-url`
- `save-path`
- `pattern`
- `replace`
- `enabled`
- `ignore-extension`
- `run-week`
- `end-date`

未表单化的字段继续由高级模式中的原始 YAML 承载。

## 方案对比

### 方案 A：主页面大表单

主页面直接铺开账号和任务的完整表单。

优点：
- 上手直观
- 实现成本较低

缺点：
- 页面会迅速变长
- 当任务数量增加时，可读性和美观度明显下降
- 不符合“更高级的管理台”目标

### 方案 B：列表 + 右侧编辑抽屉

主页面展示账号列表、任务列表和运行信息；新增或编辑时从右侧滑出抽屉表单。

优点：
- 页面主视图更干净
- 信息浏览和单项编辑可以分离
- 更接近成熟后台产品体验
- 后续继续扩展字段时也更容易维护

缺点：
- 实现复杂度高于大表单

### 方案 C：列表 + 弹窗编辑

主页面展示摘要列表，通过弹窗编辑账号和任务。

优点：
- 比大表单整洁
- 实现成本中等

缺点：
- 任务字段较多时，弹窗容易拥挤
- 长表单滚动体验较差

### 最终选择

选择方案 B：`列表 + 右侧编辑抽屉 + 高级 YAML 折叠区`。

这个方案最符合“更友好、更美观、更高级”的目标，同时仍能在当前 Spring Boot + 模板 + 原生 JS 的结构下平稳落地。

## 页面结构

主控制台重构为四个区域。

### 1. Hero 概览区

顶部保留核心操作按钮：

- 执行全部任务
- 退出登录

同时新增一组轻量统计信息：

- 账号数量
- 任务数量
- 已启用任务数量
- 最近一次手动执行时间（若存在）

Hero 区不再占据过多垂直空间，重点从“大标题”切换为“状态概览 + 关键操作”。

### 2. 账号管理区

展示账号卡片列表，每张卡片至少包含：

- 账号名称
- Cookie 已配置状态
- 关联任务数量
- 编辑按钮
- 删除按钮

顶部提供：

- 新增账号

账号信息尽量摘要化，避免在主视图中直接暴露完整 Cookie。

### 3. 任务管理区

展示任务卡片列表，每张卡片至少包含：

- 任务名称
- 所属账号
- 保存路径
- 运行星期
- 启用状态
- 单独执行
- 编辑
- 删除

顶部提供：

- 新增任务

任务卡片应明显区分“状态信息”和“操作按钮”，让用户能够快速扫视任务是否配置合理。

### 4. 配置操作区

默认仅展示结构化配置相关入口，而不是直接展示大文本框：

- 保存全部配置
- 校验配置
- 打开高级模式

高级模式展开后，才显示原始 YAML 编辑器，并附带明确提示：

- 这是高级入口
- 适用于处理表单未覆盖的字段
- 保存时仍会经过后端校验

## 编辑交互

### 账号抽屉

账号编辑使用右侧抽屉，包含：

- 账号名称
- Quark Cookie

说明文案：

- 账号名称用于任务引用，必须唯一
- Cookie 来自浏览器，程序依赖它完成自动转存

交互要求：

- 新增和编辑复用同一个抽屉
- 删除前要求二次确认
- 关闭抽屉时若存在未保存变更，需要提示

### 任务抽屉

任务编辑同样使用右侧抽屉，按分组展示。

#### 基础信息

- 任务名称
- 绑定账号
- 是否启用

#### 转存规则

- 分享链接
- 保存路径
- 文件匹配规则
- 文件名替换规则
- 忽略扩展名

#### 调度限制

- 运行星期
- 结束日期

字段辅助说明：

- 保存路径给出实际示例，例如 `/夸克自动转存/电视剧`
- 文件匹配规则提示支持正则，并给出示例 `.*\\.mp4$`
- 文件名替换规则说明允许留空
- 运行星期使用“周一到周日”的多选标签，不要求用户输入数字

## 数据模型与接口

当前配置接口只返回 `rawYaml` 和任务名列表，不足以支撑结构化表单。需要新增结构化配置读写模型。

### 新的读取结果

后端新增结构化配置返回体，至少包含：

- `accounts`
- `tasks`
- `advanced.rawYaml`

其中：

- `accounts` 用于账号列表和账号抽屉
- `tasks` 用于任务列表和任务抽屉
- `advanced.rawYaml` 用于高级模式展示当前完整 YAML

### 新的保存方式

表单保存时，前端不再直接提交 YAML 文本，而是提交结构化 JSON。

后端保存流程：

1. 接收结构化配置请求
2. 校验账号和任务字段
3. 转换为内部 `TaskFileConfig`
4. 生成标准 YAML
5. 复用现有文件保存流程原子写回 `config/tasks.yml`
6. 返回最新结构化配置和最新原始 YAML

### 高级模式保存

高级模式仍保留原始 YAML 保存接口：

- 读取时展示当前原始 YAML
- 保存时继续复用现有 YAML 语法和业务校验

这样普通用户走结构化表单，高级用户仍有兜底能力。

## 校验与错误处理

### 前端校验

前端先做基础校验，减少无意义提交：

- 名称必填
- 账号名唯一
- 任务名唯一
- 分享链接非空
- 保存路径非空
- 账号引用必须存在

### 后端校验

后端仍保留最终校验权，确保和执行逻辑一致：

- YAML 生成后的结构合法
- 账号引用存在
- 必填字段完整
- 配置文件写入失败时原文件不被破坏

### 错误展示

错误提示应尽量贴近用户语义，而不是直接显示技术异常：

- 字段级错误显示在对应输入项附近
- 保存级错误显示在抽屉顶部或配置区消息条中
- 高级模式中的语法错误明确指出是 YAML 问题

## 视觉设计方向

当前界面保留了温和背景和玻璃卡片方向，但层级偏弱、主次不够鲜明。本次重构保持青绿色主色系，同时优化以下方面：

- 顶部 Hero 区更紧凑，信息更有组织
- 卡片内容增加清晰的标题、标签、状态和说明层级
- 配置区从“大文本框”改为“操作入口 + 抽屉表单”，减少页面空洞感
- 抽屉内部使用分组标题、帮助文字、状态标签和更紧凑的间距
- 页面在桌面端和移动端都保持完整可用

视觉目标不是“极简留白”，而是“有产品质感的管理后台”。

## 对现有行为的影响

### 不影响 `once` 模式

- `once` 模式仍然按现有方式加载 `config/tasks.yml`
- GitHub Actions 继续通过 `--app.run-mode=once` 运行
- 本次改造只影响 `server` 模式下的 Web 管理台体验

### 对配置文件的影响

- 最终仍写回同一个 `config/tasks.yml`
- 不新增数据库或其他配置持久化位置
- 结构化表单只是新的编辑入口，不改变配置文件的最终消费方式

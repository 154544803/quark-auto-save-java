# quark-auto-save Java Web 管理台设计

## 背景

`quark-auto-save-java` 当前已经具备以下基础能力：

- 通过 `Spring Boot` 以默认 `server` 模式启动
- 通过 `--app.run-mode=once` 执行一次任务后退出
- 通过 `config/tasks.yml` 加载账号和任务配置
- 通过 REST 接口列出任务并触发手动执行
- 通过 GitHub Actions 在 CI 中生成 `config/tasks.yml` 并定时运行

相比 Python 版 `quark-auto-save`，Java 版目前缺少对应的 Web 管理界面，导致本地和服务器场景下的配置维护、任务查看和手动执行都依赖文件编辑或直接调用接口。

本次设计目标是在不影响 GitHub Actions 自动执行链路的前提下，为 Java 版增加一个可登录的标准管理台。

## 目标

- 为 Java 项目提供对应的 Web 管理台
- 支持用户名/密码登录保护
- 支持查看任务列表和手动执行单个或全部任务
- 支持直接读取、编辑、校验并保存 `config/tasks.yml`
- 支持查看最近一次或最近几次手动执行结果
- 保持 GitHub Actions 继续使用 `once` 模式，不被 Web 管理台影响
- 同时兼容本地启动和服务器常驻部署

## 非目标

- 不引入独立前端工程、Node 构建链或 SPA 框架
- 不把配置存入数据库
- 不改造 GitHub Actions 现有的执行模型
- 不在第一版实现插件管理、邮件配置管理、调度规则可视化编辑
- 不在第一版实现完整审计日志、权限分级或多用户管理

## 方案选择

本次选择在当前 `Spring Boot` 应用内直接集成服务端渲染管理台，而不是新增独立前端项目或拆分独立 Web 子系统。

### 备选方案

#### 方案 A：服务端渲染管理台

- 在当前应用内新增模板页面、静态资源、登录会话和管理接口
- 页面通过少量原生 JavaScript 调用 JSON API

优点：

- 只维护一个 Jar，部署方式简单
- 能直接复用现有 `server` 和 `once` 运行模式
- 对 GitHub Actions 的影响最小
- 首版实现成本最低

缺点：

- 页面交互灵活性弱于独立 SPA
- 前端复杂度上升时可维护性会逐渐下降

#### 方案 B：内嵌单页应用

- 使用单独前端构建产物并由 Spring Boot 托管静态文件

优点：

- 前后端职责更清晰
- 后续扩展复杂交互更灵活

缺点：

- 需要引入 Node 构建链
- 仓库复杂度、开发和部署成本明显增加

#### 方案 C：独立 Web 子项目

- 新建独立的 Web 管理服务，与执行器通过 API 或共享文件协作

优点：

- 隔离最彻底
- 技术选型最自由

缺点：

- 第一版成本过高
- 配置同步、认证、部署和运维都更复杂

### 最终选择

选择方案 A。在当前 Spring Boot 应用中增加管理台，是满足需求且风险最低的方案。

## 总体架构

系统继续保留两条运行路径：

- `once` 模式：启动后加载 `config/tasks.yml`，执行一次任务并退出，专供 GitHub Actions 使用
- `server` 模式：默认模式，启动 Spring Boot Web 服务，承载页面、会话登录、任务查看、手动执行和配置编辑能力

两条路径共享同一套任务执行核心和任务配置模型，但在启动行为和使用方式上完全隔离。

### 隔离原则

- GitHub Actions 继续显式传入 `--app.run-mode=once`
- `once` 模式不依赖页面、会话登录和 Web 交互
- `server` 模式新增的页面逻辑不得改变 `once` 模式的退出语义
- `config/tasks.yml` 在本地或服务器环境由管理台读写，在 GitHub Actions 环境仍由 workflow 临时生成
- 手动执行、调度执行和 `once` 模式执行复用同一个应用服务层，避免出现两套执行逻辑

## 页面设计

第一版页面包含两个入口：

- 登录页
- 主控制台

### 登录页

登录页用于收集用户名和密码，并在验证通过后写入 Session。

功能要求：

- 未登录访问页面或管理接口时跳转登录页或返回未授权状态
- 提供登录失败提示
- 提供登出能力

### 主控制台

主控制台分为三个主要区域：

#### 任务列表区

展示结构化任务信息：

- 任务名称
- 账号名
- 分享链接
- 保存路径
- 启用状态
- 可选规则信息，如 `run-week`、`end-date`

支持操作：

- 执行全部任务
- 执行单个任务

#### 执行结果区

展示最近一次或最近几次执行结果摘要：

- 执行时间
- 成功数
- 失败数
- 跳过数
- 每个任务的执行状态和摘要信息

第一版仅保存内存中的最近执行记录，不引入数据库持久化。

#### 配置编辑区

直接编辑 `config/tasks.yml` 原始内容。

第一版默认使用 YAML 文本编辑器，而不是复杂的结构化表单。这样可以：

- 避免遗漏配置字段
- 保持与现有配置格式一致
- 降低首版的建模和界面复杂度

后续如有需要，再在文本编辑基础上补充结构化表单辅助能力。

## 后端组件拆分

本次设计在现有基础上新增以下组件边界。

### 页面控制器

负责：

- 返回登录页模板
- 返回主控制台模板
- 登录成功后的页面跳转

不负责：

- 执行业务逻辑
- 直接读写任务配置文件

### 认证组件

负责：

- 校验用户名/密码
- 建立和销毁登录 Session
- 保护管理页面和管理 API

认证方式采用最轻量的会话登录，不引入 OAuth、JWT 或复杂安全框架扩展。

### 配置管理组件

负责：

- 读取 `config/tasks.yml`
- 返回原始 YAML 文本
- 对提交内容进行 YAML 语法解析
- 复用现有配置校验规则做业务校验
- 在校验通过后原子写回文件

为了避免脏写，写入流程需要保证失败时不覆盖原文件。

### 执行记录组件

负责：

- 缓存最近执行结果
- 向页面提供最近执行历史

范围控制：

- 第一版仅保留进程内内存记录
- 应用重启后历史记录允许丢失

### 现有执行服务

继续复用：

- `ApplicationRunnerService`
- `TaskExecutionService`
- `TaskConfigLoader`

必要时对 `ApplicationRunnerService` 做小幅扩展，以支持读取结构化任务详情和返回更适合页面展示的数据。

## 配置编辑流程

配置编辑使用“原始 YAML 编辑 + 后端校验”的方式。

### 读取流程

1. 前端请求配置接口
2. 后端读取 `config/tasks.yml` 原始文本
3. 后端可同时返回结构化摘要，用于页面辅助展示
4. 前端展示 YAML 内容供用户编辑

### 保存流程

1. 前端提交新的 YAML 文本
2. 后端先做 YAML 语法解析
3. 后端复用 `TaskConfigLoader` 的校验规则检查：
   - 文件结构是否正确
   - 账号是否完整
   - 任务必填项是否完整
   - 任务引用的账号是否存在
4. 全部通过后，以原子写入方式更新 `config/tasks.yml`
5. 返回保存成功结果

### 错误反馈

保存失败时至少区分两类错误：

- YAML 语法错误
- 业务校验错误

页面只展示适合用户理解的错误信息，不直接回显完整堆栈。

## 执行流程

页面上的执行操作与现有核心执行逻辑复用同一服务层。

### 执行全部任务

1. 前端点击“执行全部”
2. 后端调用应用服务执行当前配置中的全部任务
3. 执行完成后返回 `TaskExecutionSummary`
4. 同时将执行结果写入执行记录缓存

### 执行单个任务

1. 前端点击某个任务的“执行”
2. 后端按任务名过滤配置
3. 调用现有执行服务执行该任务
4. 返回执行摘要并记录到缓存

### 并发控制

第一版增加简单运行锁，避免管理台内的重复触发导致并发执行冲突。

约束如下：

- 如果当前已有手动执行在进行中，新的手动执行请求直接返回“任务正在执行中”
- 该运行锁只作用于 `server` 模式下的管理台触发
- 不改变 `once` 模式行为

调度执行是否与手动执行共用同一把锁，可以在实现阶段明确。第一版建议共用一把应用级锁，避免常驻服务下的执行重叠。

## 安全设计

第一版使用用户名/密码 + Session 的轻量认证方式。

### 配置来源

新增 Web 管理员配置，支持通过配置文件或环境变量注入：

- 用户名
- 密码

推荐优先通过环境变量注入，避免凭据固化在仓库中。

### 访问保护

以下内容必须登录后访问：

- 管理台页面
- 配置读取接口
- 配置保存接口
- 手动执行接口
- 最近执行记录接口

### 安全边界

- 不在日志中打印明文密码
- 不在页面上回显敏感配置值
- 对未授权请求返回明确的未登录状态
- `once` 模式不强依赖 Web 登录配置，避免 CI 环境因缺少管理台配置而启动失败

## 异常处理

### 配置相关异常

- 配置文件不存在时，页面给出明确提示
- YAML 语法错误时，阻止保存
- 业务校验失败时，给出具体字段级错误提示

### 执行相关异常

- 单个任务失败不阻止整批执行结果返回
- 页面优先显示任务级摘要而不是服务器堆栈
- 执行服务层继续负责汇总成功、失败和跳过结果

### 页面相关异常

- 未登录访问跳转到登录页
- 会话失效后接口返回未授权并提示重新登录

## 测试策略

### 控制器测试

覆盖：

- 登录成功和失败
- 未登录访问页面或接口时的拦截行为
- 读取配置接口
- 保存配置接口
- 执行全部任务接口
- 执行单个任务接口

### 配置服务测试

覆盖：

- 正常读取 YAML 文本
- YAML 语法错误时拒绝保存
- 业务校验失败时拒绝保存
- 校验通过时成功写回文件
- 写入失败时不破坏原文件内容

### 运行模式回归测试

覆盖：

- 默认 `server` 模式可正常启动页面
- `--app.run-mode=once` 启动后仍执行一次并退出
- 即使未配置 Web 管理员用户名/密码，`once` 模式也不受影响

### 手动验证

至少验证以下场景：

- 本地启动管理台并成功登录
- 编辑并保存 `config/tasks.yml`
- 从页面手动执行全部任务
- 从页面手动执行单个任务
- GitHub Actions 继续按原命令运行，不依赖页面

## 风险与缓解

### 风险 1：Web 管理台改动影响 `once` 模式

缓解：

- 保持 `once` 模式启动路径最小化
- 为 `once` 模式补充回归测试
- 避免在 `once` 模式中强制初始化只给页面使用的组件

### 风险 2：配置保存损坏 `tasks.yml`

缓解：

- 先解析校验，再写回文件
- 使用原子写入
- 写入失败时保留原文件

### 风险 3：重复点击导致并发执行

缓解：

- 增加运行锁
- 页面执行按钮在请求期间进入禁用状态

### 风险 4：登录保护过弱

缓解：

- 第一版至少启用会话认证
- 建议默认从环境变量加载管理员凭据
- 后续如有公网部署需求，再评估引入更完整的 Spring Security 配置

## 实现原则

- 不影响 GitHub Actions 现有自动执行路径
- 优先复用已有服务层而不是重写执行逻辑
- 先交付能稳定使用的管理台，再逐步增强页面体验
- 保持文件边界清晰，避免把页面、认证、配置和执行状态耦合在一起
